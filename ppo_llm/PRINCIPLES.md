# 工作准则（从今天的事故里长出来的）

> 一句话：**优先最简单的实现，只实现目标本身。**

## 动手前先回答三个问题（写在 commit message 或注释里）

1. **目标是什么？** 一句话，不含实现细节。
2. **怎么算成功？** 一个**数**。没有数 = 没有验收标准 = 不要动手。
3. **最少的代码路径是什么？** 只走这条路。

## 七条

| # | 规则 | 反例（今天真实发生） |
|---|---|---|
| 1 | **复用之前先看它顺带做了什么** | 复用 `rollout()` 做 eval → 顺带算 logits ✗ → chunk 卡在 8 ✗ → 每轮 eval **30 分钟** ✗ |
| 2 | **加一项功能之前，先证明症状存在** | 加了 `len_pen` / `err_pen` 防"长度膨胀" ✗ → 而"膨胀"是**我把字符当 token** 看错的 ✗✗ → 整段白写 |
| 3 | **一次只改一个变量** | adv_norm 和 LoRA 同时改 ✗ → +2.2 归因不了 ✗ |
| 4 | **每个阶段一个计时 + 一个数字上限** | eval 从来没打时间 ✗ → 吃掉 75% 墙钟而无人知 ✗ |
| 5 | **不要加"以后可能有用"的开关** | 每加一个开关，就多一条走不到的路径 ✓ 而那些路径永远没测过 ✗ |
| 6 | **超过 ~30 行的改动，先问能不能用 1/3 行数达到同一个数** | `_eval_once` 30 行够用 ✓ 而之前那版 60 行还慢 12 倍 ✗ |
| 7 | **有数学的地方写断言（这条今天做得好 ✓）；没数学的地方写数字验收标准** | PPO 有 `ratio≡1` / GAE 手算 ✓ → 一路顺畅 ✓；eval/reward 只有"能跑" ✗ → 反复返工 ✗ |

## 数字验收标准的写法（示例）

```
eval      : 500 题 ≤ 3 分钟；准确率与独立测法差 ≤ 0.5 点
判分      : 320 次 ≤ 40s；段判对率 80~95%；重试 ≤ 5%
分段      : ≥ 90% 的样本块数 ≥ 3；公式不被切断
奖励      : 与手算表逐项相等（含边界：段全对但答错、答对但段全错）
训练一步  : 生成 + 判分 + 更新 ≤ 90s（batch 32）
断点      : 崩溃最多丢 N 步；resume 后 ratio 起手仍 ≈ 1
```

## 判据：什么时候算"做多了"

- 一个改动里出现第二个**修症状**的项 → 停，先证明第一个症状真实。
- 一个函数有三个以上职责 → 拆。
- 出现"为了兼容旧行为"的分支，而旧行为**没人用** → 删。

## 保留的好习惯（别丢掉）

- 有方程的地方必须有断言（`ratio≡1`、GAE 手算、clip 边界）✓
- 改动前后跑：`py_compile` + `selfcheck.py`（含 `a.<attr>` 参数检查）+ 模块自测 ✓
- 任何 run 先 `ITERS=2 EVAL_EVERY=1`（6 分钟）✓ 再上全量 ✓

## 附：同一个病，三处（2026-10-25）

`eval` 这件事在三个地方各写了一遍，**三处都是同一个错误**：

| 位置 | 走 `rollout` → 顺带重算 logits | chunk 被卡 | 跑几遍 | 修复 |
|---|---|---|---|---|
| `prm_train._eval_once` | ✗ 是 | 8 | **2** | → vLLM 直采，**30 分钟 → 2.5 分钟** |
| `sft.evaluate_sft` | ✗ 是 | ~8 | 1 | → vLLM 直采，**15 分钟 → ~2 分钟** |
| `probe_passk` | ✗ 是（chunk 默认还是 4 ✗）| 4 | **2** | → vLLM 直采 + 贪心默认关，**40 分钟 → ~1.5 分钟** |

**根因**：`rollout` 同时做"生成 + 重算 logprobs + 算奖励"，而 eval **只需要生成**。
**教训**：**eval 只要文本** → 任何让 eval 经过训练路径的复用，都会把训练的开销一起带进来。
**验收**：`500 题 ≤ 3 分钟`。超过就是又走错路了。

## 附：第 0 条 —— **交出一条命令前，先算它要多久**

今天又犯了两次（eval 的 90 分钟、筛数据的 3.2 小时），都是**先把命令给出去，才去想代价**。

规矩：每条给用户的命令，必须带三个数：

```
单位工作量 × 次数 ÷ 吞吐 ≈ 预计墙钟
例：700 token × 16,000 次 ÷ 2,400 tok/s ≈ 1.3 小时
```

**说不出这三个数，说明我还没想清楚这条命令要干嘛。**

同一天里同一毛病的四次：eval 没计时 ✗ · grad_norm 跨程序比 ✗ · 长度字符当 token ✗ · `--limit` 照抄上次 ✗。
**共同点：动手前没有先把那个数量化。**

## 附：固定动作 —— 动手前先查三样

1. **仓库里有没有这个数？** → `grep -A22 "当前已知基线" RECORD.md`（**已记的不要重测** ✗）
2. **这条命令要多久？** → 单位工作量 × 次数 ÷ 吞吐（说不出就是没想清楚 ✗）
3. **成功长什么样？** → 一个数 + 一个区间（没有就是没有验收标准 ✗）

## 附：花 GPU 之前先算"能不能看出来"

**规则**：先写预期效应 **E**，再算当前配置的可分辨下限 **R**。**E < R 就别花 GPU** ✗。

```
R ≈ 2·sqrt(2)·SE / sqrt(种子数)      SE = sqrt(p(1-p)/题数) ≈ 2.05 点（500 题，p≈0.7）

题数 500 ·  1 种子 → R ≈ **5.8 点**
题数 500 ·  3 种子 → R ≈ **3.3 点**
题数 500 ·  7 种子 → R ≈ **2.2 点**
```

**按这个尺子，今天的账是**：

| 想回答 | 预期 E | 需要 | 值不值 |
|---|---|---|---|
| RL 有效吗（Math 基座）| +5 | 1 种子（R=5.8）| **勉强** ✓ 已做 ✓ |
| RL 有效吗（难集 / 弱基座）| +10 | 1 种子（R=5.8）| ★ **值** ✓✓ |
| **PRM vs 0/1** | +1.4 | **18 个种子** | ✗✗ **不可行 —— 别做** |
| MLP vs qkvo | ±2 | 7+ 种子 | ✗✗ 不可行 ✓ |

**结论：**"哪个变体更好"在我们预算内**测不出来** ✗ → 只能回答"训练有没有效" ✓。
**要提高分辨率**：换难集（效应 ×3 ✓ 最便宜 ✓）或加题数（线性 ✓ 但更贵 ✗）。
