# 大模型 PPO + 过程奖励（PRM）：实现说明

> 配套阅读：`PPO_THEORY.md`（公式推导）· `PRM_DESIGN.md`（判分设计）· `GRPO_THEORY.md`（对照）。
> 本文只写**我们这套实现**：大模型 PPO 的每个选择、过程奖励怎么接进去、以及踩过的坑。
> 代码入口：`prm_train.py`（训练循环）· `update.py`（PPO 更新）· `loss.py`（损失）·
> `gae.py`（优势）· `prm_reward.py`（过程奖励）· `vllm_backend.py`（rollout 与权重同步）。

---

## 1. 把语言模型当成一个 token 级 MDP

```
状态  s_t = (prompt, 已生成的前 t 个 token)
动作  a_t = 第 t 个 token（词表 152k）
策略  π_θ(a_t | s_t) = LLM 的 next-token 分布
轨迹  τ = (a_1, …, a_T)，T = 生成长度（EOS 或 max_new_tokens 截断）
奖励  **稀疏**：只在个别位置非零（见 §4）
```

**关键工程事实**：一条轨迹只有一次前向（`(B, T, V)` 的 logits），
所以策略梯度是**逐 token 的**，但奖励是**逐位置的** —— 二者靠 GAE 连接（§3）。

## 2. 损失（`loss.py`）

```
L_policy = −E[ min( r_t·A_t , clip(r_t, 1−ε, 1+ε)·A_t ) ]          r_t = exp(logπ_θ − logπ_old)
L_value  = 0.5 · E[ (V_θ(s_t) − R_t)^2 ]
L_kl     = β_kl · E[ KL(π_θ ‖ π_ref) ]                             （k3 估计量）
L_total  = L_policy + c_vf·L_value + L_kl + c_ent·L_entropy
```

**所有 reduction 都是 `masked_mean`**（分母是有效 token 数，不是 `numel()`）。
这一条不是洁癖：padding 一旦混进分母，不同 batch 的 loss 就不可比，
而"不可比"在小规模 RL 里等于**看不见训练是否在动**。

| 超参 | 我们的值 | 说明 |
|---|---|---|
| `clip_eps` ε | 0.1 | 比原论文 0.2 更紧（小模型 + LoRA，步子要小）|
| `gamma` γ | **1.0** | 无折扣：LLM 的回报不看"距终点多远" |
| `lam` λ | 0.95 | GAE 的偏差/方差折中 |
| `value_coef` | 0.5 | |
| `entropy_coef` | **0.0** | 关掉；熵项在 `(B,G,V)` 上还要额外两份张量，收益不明显 |
| `kl_estimator` | **k3** | `k3 = exp(d) − d − 1`，`d = logπ_ref − logπ`，截断 `d ≤ 10` |
| `grad_clip` | 0.5 | 实测原始 `grad_norm` 常在 0.1~1，0.5 会真的裁到 |
| `kl_coef` | 0.02 | 对 ref 的固定 KL 惩罚（不用自适应也能跑）|

**k1 vs k3**：`k1 = −d` 无下界（可以负），`k3 ≥ 0` 且更稳；
我们统一用 k3，并在 `d > 10` 处截断（防离群 token 把整批 KL 拉爆）。

## 3. 优势（`gae.py`）

```
δ_t   = r_t + γ·V(s_{t+1})·(1−done_t) − V(s_t)
A_t   = δ_t + γλ·(1−done_t)·A_{t+1}          （从后往前）
R_t   = A_t + V(s_t)                          （value 的回归目标）
```

**两个 `(1−done)` 都必须有**：
`done_t=1` 表示"这一条轨迹到此结束"（EOS 或截断），此后不能跨轨迹借信息。
漏掉第二个会让**上一条轨迹的优势渗到下一条**，而且**完全不报错**。

### 3.1 优势归一化：四种模式，只有两种是对的

| 模式 | 做什么 | 结论 |
|---|---|---|
| `batch` | 全批所有有效 token 上 `(A−μ)/σ` | ✓ **默认**：量级≈1，保留 token 级结构 |
| `grpo` | 同题 G 条之间标准化（逐样本标量）| ✓ 组相对基线；**不用 critic**；但**会抹平逐 token 的过程分** |
| `none` | 原样 | ✗ 量级随奖励设计漂移：实测比 `batch` 小 5 倍 |
| `per_sequence` | 每条序列内部标准化 | ✗✗ **致命**：每条轨迹的优势均值恒为 0 → "答对"和"答错"形状一样 → 学不到 |

**这是 PPO 实现里最容易静默坏掉的一环**，判据很干净：
把"答对"和"答错"两条序列放进同一个 batch，归一化后它们还区分得开吗？（`gae.py::_case_c`）

> 我们踩过的坑：`adv_norm` 被硬编码成 `none` → 有效步长只有常规的 1/5，
> 表现是 `approx_kl ≈ 1e-4`、`loss ≈ 0.003`，看起来"在训"其实**步子被压小了 5 倍**。

## 4. 过程奖励（PRM）怎么接进 PPO

### 4.1 奖励公式（`prm_reward.py::build_reward_matrix_paper`）

```
r_t = 0                                          （默认处处为 0）
    + β/N  @ 每个"被判对"的段落的**最后一个 token**
    + rv   @ 终止位置（done）                     rv = +1 答案对 / −1 答案错
其中 N = 该条轨迹的总段数，β = 0.15
```

**三条性质**（都在代码里有断言/自测）：

1. **段分总贡献恒 ≤ β**（每家除以自己的 N）→ 与段数无关；
2. **"答对"永远压过"答错"**：最坏情况 `−1 + β < +1`（β<1）→ 字典序保证；
3. **段分只做"同分排序"**：两条都答对时，段分高的排前面。

### 4.2 为什么段分放在**段末**而不是结尾

这是过程奖励与结果奖励的**唯一实质差别**：把奖励放在中间位置，
GAE 会让**该段内的 token 拿到正优势** → 模型学到"这一步推理本身是好的"，
而不是"整条轨迹碰巧答对了"。

代价是**信用分配的 token 数变多**：段数越多，拿到正优势的 token 越多。
这是"密集奖励会让输出变长"的机制来源（我们实测长度 +6~13%，不严重但存在）。

### 4.3 判分：大模型当"过程裁判"

```
① 按自然段落切块：空行优先；<80 字的块合并；>400 字按句切；**公式内部不切**
② 每块 → deepseek-chat → 0/1（**块级全并行**，一次发出 320 个任务）
③ 提示词要点：允许口语/犹豫；"纠正了前文错误"应给 1；乱码/夹非英文 → 0
④ 遇 0 **不停判**（停了会把"自我纠正"判成整段作废）
⑤ 前缀只给**原文**、不给"前一块判了几分"→ 于是 prompt 只依赖文本 → **全并行**
```

**第 ⑤ 条是性能关键**：一旦把"前几块的判决"写进 prompt，块与块就变成串行依赖
（每段要等前一段判完），实测 320 次判分从 26 秒变成 200 秒。

### 4.4 已知的失败模式（务必别踩）

| 模式 | 现象 | 原因 |
|---|---|---|
| **reward hacking** | 段判对率 14% → 25%，准确率不动（0.254 → 0.258）| 段分是**唯一**信号时，"写容易判对的段"比"解题"更划算 |
| **长度膨胀** | 输出变长而准确率不涨 | 上面 §4.2 的信用分配机制 |
| **判分器被骗** | 乱码块判 1 | 提示词必须显式说"乱码/夹非英文 → 0" |
| **全对恒 0** | `全对 n/32` 一直是 0 | 硬编码 `len(scores)==5`，而段落模式有 ~8 块 → **主信号全灭** |

**结论**：过程奖励**必须**和机械判据（答案对错）组合，且机械项要**定生死**（字典序），
否则一定被刷。这就是 `r = rv ± 1 + β·段分` 而不是"只用段分"的原因。

## 5. 一次训练步做了什么（`prm_train.py`）

```
每一步：
  ① 抽 8 道题 → 每题复制 G=4 份 → 32 行
  ② rollout（vLLM，0 号卡）：一次 generate 32 条 → 得到文本
  ③ 判分（外网 API）：块级全并行（~320 次调用，6s）
  ④ 重算 logπ_old（训练器，1 号卡，按行分片，no_grad）
  ⑤ 奖励：rv @ done + β/N @ 段末
  ⑥ ppo_update：GAE → 优势归一化 → 按行切 minibatch → 内层 inner_epochs 轮
      每次 backward 只喂 R 行（R = 32 / num_minibatches；实测 R=1 最稳）
  ⑦ vb.sync()：把 LoRA 权重推回 vLLM（**不 sync 就不是 on-policy**）
  ⑧ 每 5 步：原子写断点（adapter + 优化器状态 + 配置指纹）
  ⑨ 每 15 步：eval（vLLM 直采，T=1，500 题，~2.5 分钟）
```

**实测耗时（1.5B，batch 32，L40S）**：生成 45s · 判分 6s · 更新 27s ≈ **81s/步**。

### 5.1 三个"两个卡各干一件事"的硬约束

1. **vLLM 没有 `device` 参数** → 它跟 `torch.cuda.current_device()`（=0）→
   训练器必须放 `cuda:1`；
2. **权重同步走 IPC**：`live_lora_pairs(model)` 直接持有**参数张量本身** →
   优化器原地更新后自动可见 ✓（不要用 `state_dict()`，它可能是副本）；
3. **sync 必须在 eval 前、rollout 后**：否则下一次生成仍用旧权重（静默 off-policy）。

## 6. 诊断：哪些数在说什么

| 日志 | 含义 | 健康范围 |
|---|---|---|
| `ratio`（mean_ratio）| `exp(logπ_new−logπ_old)` | ★ 见下 |
| `ratio_max` | 最离群 token | 1.2~1.6（远大于 1 说明个别 token 被推狠了）|
| `approx_kl` | 策略变了多少 | 1e-3~1e-2；**1e-4 说明步长被压小** |
| `clip_frac` | 被裁的比例 | <0.1；接近 0 说明 clip 没起作用 |
| `grad_norm` | 裁剪前的梯度范数 | 0.1~1（**别拿它跨程序比** ✗）|
| `段判对率` | 判 1 的块占比 | 80~95%（<70 判分器偏严；>98 偏松）|
| `全对 n/32` | 整条都对的条数 | 20~60%（0 = 主信号死了 ✗）|

**★ `ratio ≈ 1.000x` 是正常的，不是"没在学"**：
`inner_epochs=2` 时日志记的是**第 1 轮 step 之前**的统计，那时只发生过 1 次参数更新，
`ratio − 1 ≈ lr × |∇|` 本来就极小。判断"有没有在学"要看 **eval**，
不要看 `ratio`/`loss`（`loss ≈ −mean(A)`，A 中心化后必然 ≈0）。

## 7. 超参：两套可复现的配置

| | **Math 基座（强）** | **1.5B-Instruct（弱）** |
|---|---|---|
| 基座 pass@1 | 0.664 | 0.342 |
| batch（题 × G）| 8 × 4 = 32 | 8 × 4 = 32 |
| `inner_epochs` | 2 | 2 |
| `lr` | 3e-5 | 3e-5 |
| `kl_coef` | 0.02 | 0.02 |
| `clip_eps` / `grad_clip` | 0.1 / 0.5 | 0.1 / 0.5 |
| `beta`（段分权重）| 0.15 | 0.15 |
| `adv_norm` | batch | batch |
| LoRA | r16, q/k/v/o+MLP = 18.5M | 同 |
| `max_new_tokens` | 2048 | 1024 |
| 步数 | 45 | 45 |
| **结果（T=1）** | 0.664 → **0.732**（+4.6）| 0.342 → **0.473**（+16.2，5σ）|

**两条经验**：
1. **效应大小由"基座离天花板多远"决定**：Math 基座的贪心只剩 12 点空间 → 推不动；
   1.5B 有 26 点 → 贪心也涨（+11.4）。
2. **β 太小等于没接过程奖励**：β=0.15 时单块只值 `0.15/N ≈ 0.019`，相对 `rv=±1` 是 2%
   → "PRM vs 0/1" 在 500 题下不可区分。要真的测 PRM，β 需 ≥ 0.5。

## 8. 与 GRPO 的关系

| | PPO（本文）| GRPO |
|---|---|---|
| 基线 | critic（value head）+ GAE | **组均值**（同题 G 条）|
| 优势 | 逐 token | 逐样本标量（广播到 token）|
| 内存 | 多一个 value head + 一次值估计 | 无 |
| 是否保留 token 级过程分 | ✓ | ✗（组内标准化会抹平）|

**在弱基座上两者打到同一个地方**（0.473 vs 0.481，差 0.8 点，噪声内），
所以"奖励形式/算法形式"不是主要矛盾 —— **基座余量才是**。
